# Time API Prior Art (First Pass)

This is a source survey, not an Aura design decision. Rust references are pinned to 1.85.0, Erlang/OTP source to `OTP-27.3`, and the Koka source to commit `facb7932ce6871fdb063f762a304bd8238f35fba`. Aura-specific context is the project glossary: effects are named groups of typed operations, while `Result` is an ordinary recoverable success/failure value ([`CONTEXT.md`](../../CONTEXT.md)).

## Source Facts

### 1. Wall Clock, Monotonic Clock, and Deadlines

- Rust exposes separate `SystemTime` and `Instant` point types. `SystemTime` represents the operating-system system clock and has a `UNIX_EPOCH` anchor; it is not guaranteed to move monotonically, so `duration_since` returns `Result<Duration, SystemTimeError>` when the points are in the unexpected order. `Instant` is an opaque measurement of a monotonic, nondecreasing clock and is documented as useful for measuring elapsed work. ([Rust 1.85 `SystemTime`](https://doc.rust-lang.org/1.85.0/std/time/struct.SystemTime.html), [Rust 1.85 `Instant`](https://doc.rust-lang.org/1.85.0/std/time/struct.Instant.html), [pinned standard-library source](https://github.com/rust-lang/rust/blob/1.85.0/library/std/src/time.rs#L48-L154))
- In OTP 27.3, `erlang:monotonic_time()` counts from an unspecified origin. Consecutive calls may return the same value, and monotonic values from different runtime-system instances are not comparable. `erlang:system_time()` is the runtime's view of POSIX time and is not monotonically increasing in the general case; runtime time-warp modes can alter its relationship to the monotonic clock. ([OTP 27.3 `erlang` source](https://github.com/erlang/otp/blob/OTP-27.3/erts/preloaded/src/erlang.erl#L4810-L4917), [OTP 27.3 time-correction guide](https://github.com/erlang/otp/blob/OTP-27.3/erts/doc/guides/time_correction.md#L140-L179))
- OTP's runtime timers, including `receive ... after` and BIF timers, are triggered relative to Erlang monotonic time. The guide describes millisecond timer resolution, says a timer is not allowed to trigger before its requested timeout, and notes that heavy system load can delay it. ([OTP 27.3 time-correction guide](https://github.com/erlang/otp/blob/OTP-27.3/erts/doc/guides/time_correction.md#L171-L196))

**Inference for Aura:** Monotonic points plus a duration support elapsed-time measurement and in-process deadline arithmetic without interpreting wall-clock corrections as elapsed time. Wall-clock/system points serve a different role when a value must correspond to externally meaningful civil time. OTP's timer behavior and Rust's `Instant` documentation support this distinction; they do not prescribe Aura's API or scheduling model.

### 2. Instants, Durations, and Type Distinctions

- Rust distinguishes `Instant`, `SystemTime`, and `Duration`: the first two are point types for different clock domains, while `Duration` stores a span as unsigned whole seconds plus a fractional nanosecond component. ([Rust 1.85 `Instant`](https://doc.rust-lang.org/1.85.0/std/time/struct.Instant.html), [Rust 1.85 `SystemTime`](https://doc.rust-lang.org/1.85.0/std/time/struct.SystemTime.html), [Rust 1.85 `Duration` source](https://github.com/rust-lang/rust/blob/1.85.0/library/core/src/time.rs#L58-L100))
- Erlang's `monotonic_time` and `system_time` specs both return `integer()`; the requested time unit is a separate argument. Thus the BIF signatures do not statically distinguish a monotonic count from a system-time count, or encode the count's unit in its result type. The accepted unit vocabulary includes `native`, seconds, milliseconds, microseconds, and nanoseconds. ([OTP 27.3 time-unit source](https://github.com/erlang/otp/blob/OTP-27.3/erts/preloaded/src/erlang.erl#L300-L360), [OTP 27.3 clock BIF specs](https://github.com/erlang/otp/blob/OTP-27.3/erts/preloaded/src/erlang.erl#L4810-L4917))

**Inference for Aura:** Distinct nominal point/span types make clock-domain and point-versus-span mistakes harder to express; integer counts keep representation simple but leave domain and unit distinctions to conventions or wrappers.

### 3. Precision, Units, and Range

- Rust's `Duration` has nanosecond representation, but that does not guarantee nanosecond clock precision. The `SystemTime` documentation explicitly makes precision platform-dependent and gives Windows 100-nanosecond intervals versus Linux nanosecond intervals as examples. `Duration::MAX` is about 584,942,417,355 years in the documented implementation; `checked_add` returns `Option`, while `Duration`'s ordinary `+` panics on overflow. `Instant::checked_add` also returns `Option` when the platform instant cannot represent the result. ([Rust 1.85 `SystemTime`](https://doc.rust-lang.org/1.85.0/std/time/struct.SystemTime.html), [Rust 1.85 time source](https://github.com/rust-lang/rust/blob/1.85.0/library/std/src/time.rs#L212-L219), [Rust 1.85 `Duration` source](https://github.com/rust-lang/rust/blob/1.85.0/library/core/src/time.rs#L168-L175), [checked and ordinary addition](https://github.com/rust-lang/rust/blob/1.85.0/library/core/src/time.rs#L648-L652), [addition overflow behavior](https://github.com/rust-lang/rust/blob/1.85.0/library/core/src/time.rs#L1115-L1121), [instant checked addition](https://github.com/rust-lang/rust/blob/1.85.0/library/std/src/time.rs#L389-L397))
- OTP's `native` unit is determined when a runtime starts and may differ after a restart. OTP warns that the unit scale alone says little about accuracy; `convert_time_unit/3` rounds down and can lose accuracy and precision. ([OTP 27.3 time-unit source](https://github.com/erlang/otp/blob/OTP-27.3/erts/preloaded/src/erlang.erl#L300-L360), [OTP 27.3 conversion source](https://github.com/erlang/otp/blob/OTP-27.3/erts/preloaded/src/erlang.erl#L4899-L4935))
- OTP documents timer resolution as milliseconds at the API and runtime levels; under heavy load, a timer may fire later than its nominal window. ([OTP 27.3 time-correction guide](https://github.com/erlang/otp/blob/OTP-27.3/erts/doc/guides/time_correction.md#L181-L196))

### 4. UTC, Civil Time, and Daylight-Saving Transitions

- Erlang's calendar documentation defines local time as adjusted for the current time zone and daylight saving, and universal time as UTC without daylight-saving adjustment. `universal_time_to_local_time/1` converts UTC to local time. ([OTP 27.3 `calendar` source](https://github.com/erlang/otp/blob/OTP-27.3/lib/stdlib/src/calendar.erl#L22-L35), [UTC-to-local conversion](https://github.com/erlang/otp/blob/OTP-27.3/lib/stdlib/src/calendar.erl#L764-L773))
- `local_time_to_universal_time_dst/1` returns a list with zero, one, or two UTC candidates: zero for a skipped local time during the switch to daylight saving, two for a repeated local time during the switch back, and one otherwise. The older `local_time_to_universal_time/1` is deprecated because it still returns a result for a skipped local time. These conversion functions take a local date-time tuple and no explicit zone identifier. ([OTP 27.3 `calendar` source](https://github.com/erlang/otp/blob/OTP-27.3/lib/stdlib/src/calendar.erl#L399-L453))

**Inference for Aura:** Local civil time to UTC is not always a one-to-one conversion. An API must choose how to expose a nonexistent or ambiguous local time, and a host-local conversion is not the same contract as conversion through an explicitly selected time zone.

### 5. Clock Reads and Effects

- Rust exposes `Instant::now() -> Instant` and `SystemTime::now() -> SystemTime` directly; the read signatures have no `Result` return. Ordering failures are reported by `SystemTime::duration_since`, while `Instant::checked_duration_since` can return `None` for a reversed or anomalous measurement. ([Rust 1.85 `Instant` and `SystemTime` source](https://github.com/rust-lang/rust/blob/1.85.0/library/std/src/time.rs#L271-L341), [Rust `SystemTime` methods](https://github.com/rust-lang/rust/blob/1.85.0/library/std/src/time.rs#L510-L579))
- Erlang exposes clock reads as BIFs whose specs return integers; those signatures do not include an effect row or a recoverable-result type. ([OTP 27.3 `erlang` source](https://github.com/erlang/otp/blob/OTP-27.3/erts/preloaded/src/erlang.erl#L4810-L4917))
- Koka's first-party `std/time/timer` source exposes `ticks()` as `ndet duration`, documents it as a monotonic high-resolution timestamp with at least millisecond resolution, and types `elapsed` with `<ndet|e>` while running an action with that effect row. This is a concrete effect-annotated clock-read example; the cited declarations use `ndet`, not a time-named effect. ([Koka source at pinned commit](https://github.com/koka-lang/koka/blob/facb7932ce6871fdb063f762a304bd8238f35fba/lib/std/time/timer.kk#L27-L54))

**Inference for Aura:** Clock access and recoverable failure are separate modeling questions. Aura could make a clock read visible as a typed operation or expose a direct API; either choice can separately define whether platform/read failures are returned as `Result` values. The examples above show differing API surfaces, not a winning design.

## Options and Tradeoffs (Not a Recommendation)

- **Separate clock-domain types versus integer counts:** separate wall/system and monotonic points, plus a span type, improve static distinction at the cost of explicit conversions. Integer counts are compact and easy to bind to a runtime, but callers must preserve the domain and unit; OTP's `native` scale can vary across runtime restarts. ([OTP 27.3 time-unit source](https://github.com/erlang/otp/blob/OTP-27.3/erts/preloaded/src/erlang.erl#L300-L360))
- **UTC/system points versus civil values with zones:** an epoch-oriented point is useful for interchange, while civil-time conversion needs zone rules and explicit behavior for daylight-saving gaps/folds. Host-local conversion is convenient but inherits the runtime's local-zone configuration. ([OTP 27.3 `calendar` source](https://github.com/erlang/otp/blob/OTP-27.3/lib/stdlib/src/calendar.erl#L22-L35), [DST conversion source](https://github.com/erlang/otp/blob/OTP-27.3/lib/stdlib/src/calendar.erl#L399-L453))
- **Explicit clock effect versus direct clock API:** an effect makes the read visible in Aura's typed effect model and can be interpreted by a handler; a direct API has a smaller surface. In either case, `Result` can remain the ordinary value channel for recoverable failures, as Aura's glossary defines it. These are tradeoffs for the ticket to resolve, not a selection. ([Aura glossary](../../CONTEXT.md), [Koka timer source](https://github.com/koka-lang/koka/blob/facb7932ce6871fdb063f762a304bd8238f35fba/lib/std/time/timer.kk#L27-L54))
