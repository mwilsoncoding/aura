# Koka Effect Handling: Research Notes

**Scope.** This report describes the Koka language book and implementation at source revision [`64324ad`](https://github.com/koka-lang/koka/tree/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8). The primary design papers are Daan Leijen's [*Koka: Programming with Row-Polymorphic Effect Types*](https://arxiv.org/abs/1406.2061) and Xie et al.'s [*A Formalization of Effect Handlers in Koka*](https://doi.org/10.1145/3158096). The claims below describe these sources, not a recommendation that Aura adopt Koka's choices.

## Effect typing and inference

**Observed in Koka.** A function type carries its effect between the argument and result types. The empty effect is `total`/`<>`; named effects include exceptions, divergence, console I/O, and user-declared effects. The compiler infers effects, and an effectful call either has its effect handled in the surrounding context or propagates that effect in the caller's type. [Koka book: effect types](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/doc/spec/tour.kk.md#L452-L495) [Koka book: declaring and using an effect](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/doc/spec/tour.kk.md#L949-L978)

Effects compose as rows. A row can have a polymorphic tail (`<l|e>`); a higher-order function such as `map` can therefore preserve the callback's unknown effect, while `while` adds divergence. At a call site, Koka extends and unifies the argument effects so the result accounts for both effects and the loop's own divergence. This is row polymorphism and effect inference, not a claim that Koka's *value types* use set-theoretic unions. [Koka book: combining and polymorphic effects](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/doc/spec/tour.kk.md#L529-L593) The book also states that its inference does not prove arbitrary recursive functions terminate, so it conservatively assigns `div` in the Fibonacci example. [Koka book: termination inference limitation](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/doc/spec/tour.kk.md#L610-L613)

**Possible Aura implication.** If Aura combines effect tracking with set-theoretic value types, the two algebras need an explicit boundary: effect-row union/unification is not automatically value-type union/subtyping. Decide whether effect rows are normalized sets, multisets, or another structure before relying on set-like intuition: Koka's `mask` example deliberately yields duplicate labels to represent nested handler layers. [Koka book: masking and duplicate labels](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/doc/spec/tour.kk.md#L1541-L1575)

## Handler semantics

**Observed in Koka.** An effect declaration introduces operations; using one adds its effect to the function type. A handler scopes over an action, intercepts an operation at its innermost matching handler, and can discharge that effect from the result type. A `ctl` clause gets a resumption: calling `resume(value)` continues at the operation's call site, while returning directly abandons that continuation. The `ask` example resumes twice through the same handler, showing that the resumed computation is handled again by that handler. A handler's `return` clause transforms the action's normal result. [Koka book: handling and discharging an effect](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/doc/spec/tour.kk.md#L949-L1034) [Koka book: resumption](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/doc/spec/tour.kk.md#L1042-L1098) [Koka book: return clauses](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/doc/spec/tour.kk.md#L1372-L1391)

Koka distinguishes general `ctl` operations from tail-resumptive `fun` operations. A general continuation may be resumed zero, one, or multiple times; multiple resumption can implement nondeterministic branching. `fun` operations constrain handlers to the tail-resumptive case. `linear effect` further restricts an effect to tail-resumptive operations and linear effects, enabling the compiler to avoid the general monadic translation for that code. [Koka book: tail-resumptive operations](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/doc/spec/tour.kk.md#L1101-L1160) [Koka book: multiple resumptions](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/doc/spec/tour.kk.md#L1713-L1755) [Koka book: linear effects](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/doc/spec/tour.kk.md#L1889-L1895)

The implementation's handler-inference path checks the handler type and calls `checkLinearity` for a linear effect, so this restriction is enforced by the compiler rather than being only descriptive prose. [Koka source: `Type.Infer.inferHandler`](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/src/Type/Infer.hs#L1042-L1059)

The freedom to resume multiple times has a resource-management cost: the book's file-handler example warns that a second resumption could close the same file twice and says this is not statically prevented by the presented design. Koka provides `initially`/`finally` for lifecycle behavior, but the source calls out this interaction as a constraint. [Koka book: resumptions and external resources](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/doc/spec/tour.kk.md#L1796-L1851)

Koka's stated tradeoffs are that handlers have Hindley–Milner-style types without the answer-type rules needed for `shift`/`reset`, delimit resumptions (unlike `call/cc`), and compose through a free-monad account; not every monad, including the continuation monad, is expressible as an effect handler. The implementation nevertheless uses delimited control internally and allocates continuations when a general `ctl` operation yields. [Koka book: handler tradeoffs and compilation](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/doc/spec/tour.kk.md#L1481-L1500) These semantics and implementation are treated more formally in the Koka authors' [handler formalization](https://doi.org/10.1145/3158096); the earlier Koka paper develops its row-polymorphic effect typing ([Leijen 2014](https://arxiv.org/abs/1406.2061)).

**Possible Aura implication.** The choices that most affect Aura's model are whether handlers are deep (Koka's resumed `ask` example behaves this way), whether resumptions may be duplicated or discarded, whether normal returns have a handler clause, and how effects performed by handler clauses are represented. If Aura wants multi-shot control, resource ownership/finalization needs a deliberate story; if it wants a simpler first implementation, a tail-resumptive-only subset is a meaningful restriction, not an equivalent implementation of general `ctl`.

## Design questions for Aura

- Specify effect-row combination and constraints independently of Aura's value-type union/intersection and subtyping rules.
- Choose and document handler depth, operation resumption cardinality, and whether the continuation can escape its handler's scope.
- Decide whether to include Koka-style masking/nested same-effect handlers; masking creates meaningful repeated labels in rows.
- Decide how handler clauses contribute effects and how multi-resumption interacts with resources, mutation, and concurrency.
- Treat termination inference, linear effects, and compilation strategy as separate decisions; Koka's `div`, linear-operation restriction, and continuation-allocation strategy are related but distinct mechanisms.

These are design prompts, not conclusions forced by the Koka sources or by Aura's stated goals. Aura is exploratory, and the README lists Koka-style effect handling as an influence rather than a settled specification.
