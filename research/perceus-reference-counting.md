# Perceus Reference Counting and Reuse

## Scope

The primary paper is Alex Reinking, Ningning Xie, Leonardo de Moura, and Daan Leijen, “Perceus: Garbage Free Reference Counting with Reuse,” published at PLDI 2021; Microsoft Research hosts the authors’ extended version and the ACM record identifies the proceedings paper ([author-hosted extended paper](https://www.microsoft.com/en-us/research/wp-content/uploads/2020/11/perceus-tr-v4.pdf), [Microsoft Research publication page](https://www.microsoft.com/en-us/research/publication/perceus-garbage-free-reference-counting-with-reuse/), [ACM DOI](https://doi.org/10.1145/3453483.3454032)). Implementation observations below are pinned to Koka commit [`64324ad`](https://github.com/koka-lang/koka/commit/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8), rather than treated as universal requirements of the paper.

## Observed in the Paper

Perceus translates a functional core language with explicit control flow into precise reference-count operations; its stated goal is to reclaim objects as soon as their last reference disappears and to reuse storage, and the authors present the algorithm as sound and garbage-free ([paper, abstract and algorithm](https://www.microsoft.com/en-us/research/wp-content/uploads/2020/11/perceus-tr-v4.pdf)). The core ownership mechanism is compiler-managed accounting: `dup` accounts for another live reference, while `drop` discharges a reference whose lifetime ends; this is not, by itself, a claim that Aura must expose a programmer-written ownership type system ([paper](https://www.microsoft.com/en-us/research/wp-content/uploads/2020/11/perceus-tr-v4.pdf); Koka’s `Parc` pass emits and optimizes these operations in [control-flow branches](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/src/Backend/C/Parc.hs#L292-L350)).

Reuse is an optimization enabled by uniqueness: after the final reference to a suitable object is dropped, its storage can hold a new object rather than requiring another allocation. If the old object is still shared, it must remain valid for its other references, so reuse cannot mutate that block; Koka validates a reuse token before using it and otherwise constructs the value normally ([paper](https://www.microsoft.com/en-us/research/wp-content/uploads/2020/11/perceus-tr-v4.pdf); Koka’s [uniqueness branch](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/src/Backend/C/ParcReuse.hs#L249-L269) and [reuse-validity fallback](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/src/Backend/C/ParcReuseSpec.hs#L152-L175)).

## Observed in Koka

Koka’s `ParcReuse` pass records deconstructed values as reuse candidates with allocation size and scan-field count, and makes candidates available when the corresponding value is dropped ([candidate registration](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/src/Backend/C/ParcReuse.hs#L276-L286), [pattern/deconstruction analysis](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/src/Backend/C/ParcReuse.hs#L322-L340)). A constructor allocation consumes only a candidate in the same byte-size bucket; with none available, it remains a normal allocation. This implementation excludes zero-sized and `Just`-like constructors, and constructors marked `_noreuse` ([eligibility and exact-size selection](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/src/Backend/C/ParcReuse.hs#L357-L384)).

The compiler can specialize a reused block by writing the replacement constructor fields and, where needed, its tag and scan layout ([specialized rewrite](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/src/Backend/C/ParcReuse.hs#L110-L125)). At runtime, Koka represents a thread-local unique block with reference count `0`; `drop_reuse` at that count drops the old block’s scanned children and returns its storage, while a shared or sticky count follows ordinary drop handling and returns a null reuse token ([runtime drop-reuse](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/kklib/src/refcount.c#L213-L232), [inline drop-reuse API](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/kklib/include/kklib.h#L794-L834)).

The `0`-means-unique convention and the remaining count encoding are Koka choices, not a paper-level ABI: its runtime uses positive counts for local references, negative encodings for thread-shared references, atomic operations for shared counts, and sticky states for some overflow cases ([Koka runtime count invariants and memory ordering](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/kklib/src/refcount.c#L89-L210)). Reuse also depends on a sound layout/size estimate: the pinned Koka change specifically fixes function values being incorrectly treated as fixed-size donors, because closure size depends on captures; the accompanying regression test checks that a dropped closure is not reused for a constructor ([fix and rationale](https://github.com/koka-lang/koka/commit/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8), [regression test](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/test/parc/parc-closure-reuse.kk#L1-L8)).

Reference counting alone does not reclaim an unreachable cycle whose internal references keep all counts nonzero; the cited Koka drop path recursively decrements children only after a block reaches zero and does not show a cycle collector ([runtime drop path](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/kklib/src/refcount.c#L23-L80), [count-zero reuse path](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/kklib/src/refcount.c#L213-L232)). Thus cycle formation/collection is a language-runtime constraint to settle if Aura permits cyclic heap graphs; this is a consequence of the reference-count mechanism, not a claim that the cited paper prescribes one Aura policy.

## Possible Implications for Aura

- Decide whether ownership is only a compiler invariant that lowers to `dup`/`drop`, or also a user-facing type/API contract; Perceus demonstrates the former and does not settle Aura’s surface syntax ([paper](https://www.microsoft.com/en-us/research/wp-content/uploads/2020/11/perceus-tr-v4.pdf)).
- Specify which values may be reused: require a runtime uniqueness proof, compatible allocation size/layout, and a fresh-allocation fallback. Define behavior for closures, dynamically sized objects, mutation, and foreign values before enabling reuse ([Koka’s eligibility and fallback](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/src/Backend/C/ParcReuse.hs#L357-L384); [closure-size regression](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/test/parc/parc-closure-reuse.kk#L1-L8)).
- Resolve cycle handling, cross-thread sharing/atomicity, and reference-count overflow semantics as explicit runtime decisions; Koka’s encoding is one concrete design, not a requirement inherited from Perceus ([Koka count invariants](https://github.com/koka-lang/koka/blob/64324ad9f4b7d607573c49f4f26eb9ac475d2aa8/kklib/src/refcount.c#L89-L210)).
