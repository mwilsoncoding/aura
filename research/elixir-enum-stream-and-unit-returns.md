## 1. Enumerable, Enum, and Stream

`Enumerable` is the shared protocol used by `Enum` and `Stream`. Its contract requires `reduce/3`, `count/1`, `member?/2`, and `slice/1`; `reduce/3` is the core traversal operation, while the other callbacks let a type provide faster answers. A reducer signals continue, halt, or suspend with `{:cont, acc}`, `{:halt, acc}`, or `{:suspend, acc}`; the result is `{:done, acc}`, `{:halted, acc}`, or `{:suspended, acc, continuation}`. ([Protocol definition and requirements](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/lib/enum.ex#L5-L55); [reducer and result types](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/lib/enum.ex#L75-L126))

`Enum` functions are eager: they begin traversing when called, and operations such as `Enum.map/2` return a list. Elixir explicitly warns that eager operations are unsafe on infinite enumerables when they require unbounded traversal. ([Enum module documentation](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/lib/enum.ex#L251-L303); [`Enum.map/2`](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/lib/enum.ex#L1706-L1734))

`Stream` functions instead create composable, lazy enumerables. Chaining stream transformations constructs a recipe; computation starts when an enumerable consumer such as `Enum` traverses it. `Stream` itself implements `Enumerable`, which is why a stream can be passed directly to `Enum`. ([Stream documentation](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/lib/stream.ex#L5-L80); [Stream's Enumerable implementation](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/lib/stream.ex#L1766-L1785))

The v1.20.4 `Stream` API has no `sort/1` or `sort_by` operation ([versioned Stream function index](https://hexdocs.pm/elixir/1.20.4/Stream.html#functions)). Sorting is an `Enum` operation: `Enum.sort/1` follows Erlang term ordering, uses merge sort, and returns a list; applied to a stream, it is an eager terminal operation, not a lazy stream transformation. ([`Enum.sort/1` and `/2`](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/lib/enum.ex#L3208-L3325))

`Enum.sort/1` has the default term-order behavior. `Enum.sort/2` accepts a two-argument Boolean sorter, `:asc`, `:desc`, a module implementing `compare/2`, or `{:asc | :desc, module}`. A Boolean sorter should return `true` when its first argument precedes or ties the second; stability requires returning `true` for equal values. A comparison module returns `:lt`, `:eq`, or `:gt`; Elixir documents `Date.compare/2` as the semantic alternative to structural comparison for dates. ([Sorter contract and options](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/lib/enum.ex#L3229-L3325))

`Enum.sort_by/2` and `/3` take a mapper, with the third argument defaulting to `:asc`. The mapper is evaluated once per element; the sorter compares the mapped values, and accepts the same direction/module forms as `sort/2`. The docs likewise warn that default structural ordering is often wrong for structs. ([`sort_by` docs and options](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/lib/enum.ex#L3327-L3392); [arities and implementation](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/lib/enum.ex#L3431-L3452))

`Enum.flat_map/2` accepts any enumerable from its callback and eagerly materializes the one-level flattening as a list. `Stream.flat_map/2` returns a lazy stream and consumes each callback-produced enumerable only as the result stream is traversed. `Enum.reduce/3` is the explicit-initial-accumulator eager reduction; the docs describe reduce (sometimes called fold) as a basic building block for Enum operations. ([`Enum.flat_map/2`](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/lib/enum.ex#L1242-L1286); [`Stream.flat_map/2`](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/lib/stream.ex#L491-L544); [`Enum.reduce/3`](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/lib/enum.ex#L2613-L2654))

Maps are enumerable as `{key, value}` pairs: the built-in `Enumerable.Map` implementation reduces over `:maps.to_list/1`. Elixir's `Map` documentation explicitly says map entries do not follow any order, so callers must not rely on raw map traversal order. `Enum.sort(map)` returns a sorted list of entry tuples, not a sorted map. ([Map implementation](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/lib/enum.ex#L5122-L5143); [Map ordering documentation](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/lib/map.ex))

Ordinary structs do not inherit the Map `Enumerable` implementation: protocol dispatch looks up the struct's own implementation, and protocols default to no `Any` fallback. A struct must implement `Enumerable` (or use a fallback explicitly provided by that protocol). ([struct protocol dispatch and fallback default](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/lib/protocol.ex#L812-L818); [dispatch implementation](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/lib/protocol.ex#L928-L975))

## 2. Side Effects and Return Values

`Enum.each/2` returns `:ok`. Its callback is typed `element -> any`; for non-lists the implementation calls the callback and discards its return value for each traversed element, then returns `:ok` (the list path delegates to `:lists.foreach/2`). ([`Enum.each/2` docs, spec, and implementation](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/lib/enum.ex#L963-L993))

`Stream.each/2` is different: it returns a lazy stream that runs the callback during later traversal and passes each original element onward. `Stream.run/1` is the consume-for-effects operation and returns `:ok` after reducing the stream. ([`Stream.each/2`](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/lib/stream.ex#L477-L503); [`Stream.run/1`](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/lib/stream.ex#L695-L709))

In Erlang, `ok` is an atom commonly used as a successful operation result: for example, `io:put_chars/1` is specified to return `'ok'`, while `file:write_file/2` returns `ok | {error, Reason}`. The Erlang reference's predefined/built-in type lists contain no dedicated `unit()` type; `none()` and `no_return()` denote no normal result/terms, not a one-value Unit. ([`io:put_chars/1`](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/lib/stdlib/src/io.erl#L247-L254); [`file:write_file/2`](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/lib/kernel/src/file.erl#L1188-L1194); [atom syntax](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/system/doc/reference_manual/data_types.md#L195-L199); [predefined and built-in types](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/system/doc/reference_manual/typespec.md#L89-L187) and [built-in aliases](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/system/doc/reference_manual/typespec.md#L192-L226))

## 3. Koka and Verse

Koka's book distinguishes `:void`, which has no alternatives and therefore no value, from `:unit`, which has exactly one constructor/value, `Unit`. `:()` is shorthand for the unit type and `()` for its value. ([Koka v3.2.9 language tour](https://github.com/koka-lang/koka/blob/facb7932ce6871fdb063f762a304bd8238f35fba/doc/spec/tour.kk.md#L792-L797))

Unit-returning effectful computations are conventional in Koka's own standard library: the `console` effect is documented as allowing console output, and `string/println` has type `console ()`. ([Koka console effect](https://github.com/koka-lang/koka/blob/facb7932ce6871fdb063f762a304bd8238f35fba/lib/std/core/console.kk#L22-L24); [`print`/`println` signatures](https://github.com/koka-lang/koka/blob/facb7932ce6871fdb063f762a304bd8238f35fba/lib/std/core/console.kk#L69-L83))

The pinned Verse book explicitly presents a result convention: it says `void` is used when there is no meaningful result, that effect-focused functions have return type `void`, and gives a printing `LogMessage` example. It also says the single "nothing interesting here" value is written `false` or `()`, with `void`, `true`, and `tuple()` describing it. ([Verse book, `void` and unit-like value](https://github.com/VerseLang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/docs/02_primitives.md#L1208-L1258))

That is direct evidence of a Verse no-result convention, but its exact type semantics are not internally consistent in this revision: the Types chapter calls `void` the universal supertype containing all values and `false` the empty/bottom type, while the primitive chapter presents `void` alongside `true` and `tuple()` as describing one value. The official `Void.versetest` also accepts an arbitrary body expression for a `:void` return (`F0():void = 1`). Treat the documented usage convention as evidence, but do not assume a single unambiguous formal equivalence to Koka's unit without resolving this source discrepancy. ([Verse Types chapter](https://github.com/VerseLang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/docs/11_types.md#L1224-L1237); [Verse void test](https://github.com/VerseLang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/Tests/Void.versetest#L3-L13))

## 4. `for` Comprehension Follow-Up

This is a separate comparison, not an enumeration-ticket resolution. Elixir's `for` returns a list by default and evaluates its generators while the comprehension is evaluated. `<-` extracts values from enumerables and matches them against the left-hand pattern; multiple generators nest, filters discard falsy values, and failed generator patterns filter out values. The implementation lowers enumerable generators to `Enum.reduce` calls. ([`Kernel.SpecialForms.for/1` docs](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/lib/kernel/special_forms.ex#L1395-L1434); [compiler lowering](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/src/elixir_erl_for.erl#L238-L260))

The `:into` option directs results into any `Collectable`; it changes the destination, not the generator syntax into a lazy `Stream` pipeline. The compiler obtains a `Collectable.into` accumulator and runs the generated reductions. The docs also show `:uniq` as a separate option. ([`for` collection options](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/lib/kernel/special_forms.ex#L1476-L1504); [compiler `Collectable.into` and reduction](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/src/elixir_erl_for.erl#L171-L200))

## 5. Keyword Lists and Aura Boundary

Elixir defines a keyword list as a list of two-element tuples whose keys are atoms and whose values are arbitrary terms. Duplicate keys are allowed; `Keyword.get/3` returns the first matching value, while `Keyword.put/3` and `Keyword.delete/2` remove all duplicates. Although the underlying list order is preserved, Keyword functions do not promise where a new key is inserted; `put` may add it at the front, end, or elsewhere. ([Keyword module documentation](https://github.com/elixir-lang/elixir/blob/759443e724f55bf58e71c0603644e99058918d52/lib/elixir/lib/keyword.ex#L5-L67))

Aura's current glossary says struct values may carry additional map fields but struct enumeration covers only declared fields, so Elixir's map-entry enumeration should not be transferred wholesale to Aura ([Aura context](../CONTEXT.md#L23-L24)). An ordered list of two-element tuples beginning with atoms is the proposed Keyword list shape. `[{atom, dynamic}]` and `list(tuple(atom, dynamic))` are illustrative descriptions only; no type spelling, dedicated type, or API has been decided. Lookup and duplicate-key semantics also remain open.

## Aura Design Questions (Not Decisions)

- Preserve the distinction between default traversal and sorting: Elixir maps have no guaranteed traversal order, while `Enum.sort/1` uses Erlang term order. Aura's contract should say which sequence each enumerable exposes and what `sort/1` means; custom sorters or key projections provide explicit caller control.
- Aura's currently agreed struct behavior (enumerate declared fields in declaration order) is intentionally different from Elixir, where structs are not enumerable by default unless they implement `Enumerable`.
- Koka demonstrates a real Unit value for effectful operations. Elixir and Erlang instead use `:ok`/`ok` as ordinary success atoms, while Verse's public source does not provide an unambiguous Unit equivalent. Aura's type-system decision includes Unit as a value type distinct from the `nil` atom; that is a design decision, not an implementation fact. `Enum.each`'s return contract remains open ([Choose Aura type-system contract](https://github.com/mwilsoncoding/aura/issues/8)).
- Elixir's `for` semantics are a separate follow-up to the current Enum/Stream decision.

No Aura behavior or issue decision is resolved by this report.
