# Transactional Memory and Perceus Compatibility

Research for [issue #39](https://github.com/mwilsoncoding/aura/issues/39), as of 2026-09-29.

## Finding

The reviewed sources show no inherent contradiction between software transactional memory (STM) and compiler-managed reference counting (RC). They do not, however, establish a drop-in integration with Perceus. A transaction that stages pointer/root changes can in principle preserve Perceus-managed values; a transaction that destructively reuses an existing object must also preserve isolation and enough prior state to roll back. The latter needs explicit coordination of transaction logs, object ownership, reference-count changes, allocation, and reclamation. Neither correctness nor performance of that combined design is proved by the sources reviewed here.

This is a statement of technical constraints and evidence limits, not a recommendation to include or exclude transactional memory from Aura.

## Established Results

**Perceus and reuse.** Reinking et al. present Perceus as a compiler algorithm for precise reference counting over a functional core language with explicit control flow. The paper proves soundness and “garbage freedom” for cycle-free programs, and describes reuse analysis that enables guaranteed in-place updates while retaining a functional programming interface ([Perceus paper, POPL 2021](https://doi.org/10.1145/3453483.3454032)). That result is not a proof about STM transactions or rollback.

Koka's first-party compiler implementation makes the reuse condition concrete: its reuse pass emits the reuse assignment when the value is unique; otherwise it performs the shared drop/decrement path. It also carries eligible deconstructed values through the reuse analysis ([Koka `ParcReuse.hs`](https://github.com/koka-lang/koka/blob/8b803da69d3941ce1e03173578093aefc41ee548/src/Backend/C/ParcReuse.hs#L238-L285)). The runtime represents a same-thread unique reference with count zero and uses separate thread-shared count states; shared increments/decrements are atomic, and the final shared decrement uses acquire ordering before freeing the object ([Koka `refcount.c`](https://github.com/koka-lang/koka/blob/8b803da69d3941ce1e03173578093aefc41ee548/kklib/src/refcount.c#L99-L148), [drop/reuse paths](https://github.com/koka-lang/koka/blob/8b803da69d3941ce1e03173578093aefc41ee548/kklib/src/refcount.c#L189-L230)). Thus Koka demonstrates that Perceus-style RC can account for references shared across threads. These atomics govern object lifetime; by themselves they do not provide transaction isolation or rollback.

**STM isolation and commit.** Two primary STM designs illustrate useful variants. Harris et al.'s composable STM paper describes transactions composed over transactional variables and operations such as retry/choice ([Composable Memory Transactions, POPL 2005](https://doi.org/10.1145/1065944.1065952)). Dice, Shalev, and Shavit's TL2 is a versioned, lock-based STM design with validation ([Transactional Locking II, DISC 2006](https://doi.org/10.1007/11864219_14)). These are algorithm families, not evidence that arbitrary heap mutation is automatically transactional.

GHC's first-party STM runtime documents per-TVar exclusion with optimistic reads and version information; the documented fine-grained mode permits dynamically non-conflicting transactions to commit in parallel ([GHC `STM.h`](https://github.com/ghc/ghc/blob/9f48a5b908f572847bc8ba4657c9f5a5d4284556/rts/STM.h#L9-L26)). Its read/write operations keep `expected_value` and `new_value` in transaction records rather than immediately replacing the TVar's value ([GHC `STM.c`, read/write](https://github.com/ghc/ghc/blob/9f48a5b908f572847bc8ba4657c9f5a5d4284556/rts/STM.c#L1468-L1547)). At commit it validates and acquires ownership, then publishes the new values; a failed validation releases ownership ([GHC `STM.c`, commit](https://github.com/ghc/ghc/blob/9f48a5b908f572847bc8ba4657c9f5a5d4284556/rts/STM.c#L1256-L1323)). Abort marks the record aborted; for a nested abort, it merges the read set into its parent ([GHC `STM.c`, abort](https://github.com/ghc/ghc/blob/9f48a5b908f572847bc8ba4657c9f5a5d4284556/rts/STM.c#L917-L949)). This log-and-publish arrangement avoids needing to undo writes to the TVar during ordinary abort. It is an STM over TVars, not a demonstration of rollback for arbitrary in-place updates inside the values those TVars reference.

## Integration Constraints

The following are consequences of combining the mechanisms above; they are design obligations, not results proved by either body of work.

| Concern | Constraint for a combined runtime |
| --- | --- |
| Isolation and conflict detection | RC answers whether references keep an object alive and whether reuse may be allowed; STM answers whether a transaction's observed locations remained valid and which writes conflict. One signal cannot replace the other. Mutable locations must have STM-visible versions/locks or be reached through transactional indirection. A conflict must prevent or discard the speculative update, not merely adjust a reference count. |
| Rollback and commit | With buffered writes, abort can discard the transaction's proposed values; successful commit publishes them. If an existing Perceus object was overwritten in place, abort needs an undo log/snapshot or another preserved old version. Reuse cannot destroy the only rollback copy before the transaction is irrevocable. Commit also needs to transfer ownership of new references and retire replaced references exactly once. |
| Allocation and reclamation | Objects allocated speculatively must not become visible before commit. Abort must reclaim transaction-private allocations and their child references; commit must make their ownership visible before private transaction roots are released. Values held by read/write logs, retry state, or concurrent readers must remain alive until those holds end. In an RC design, those roots and release points need explicit accounting or an equivalent reclamation protocol. |
| Mutation and uniqueness | Perceus reuse is conditional on uniqueness. A transaction's saved old value, read-set entry, or another thread's snapshot is an additional logical observer unless the ownership protocol represents it another way. Reuse of a pre-existing value is therefore unavailable when that reuse would mutate state a transaction may still read or need to restore. Transaction-private allocations are a narrower plausible reuse case. |
| Ownership and counts | Duplicating a value into a transaction log, replacing a staged value, aborting, and committing each affect object ownership. Updates can be eagerly counted and reversed, deferred to commit, or represented by transaction-local ownership; each alternative needs to keep counts consistent with all live pointers and with the uniqueness test. This policy is not specified by the Perceus or STM sources above. |
| Conflicts and cost | STM adds log entries, validation, synchronization on writes, and possible re-execution after conflict. Thread-shared Perceus references may require atomic count operations. A combined implementation could add count traffic for log-held values and allocation/drop work for retries, while contention can amplify both. This cost interaction is plausible from the separate mechanisms; the reviewed sources provide no combined benchmark or cost model. |

## Plausible Combinations, Not Established Results

1. **Transactional roots over persistent values.** Keep transactionally mutable state in TVars or equivalent root cells, while their payload graphs are not destructively changed during a transaction. A transaction stages a replacement root; commit publishes it, while abort releases staged values. Perceus could manage payload lifetimes if log and root references are included in accounting. This resembles GHC's log-and-publish boundary, but an STM-plus-Perceus implementation and proof are not supplied by the cited work.
2. **Transactional object fields with deferred writes.** Track versions/ownership for every mutable field, buffer writes, and only mutate or publish after validation. Existing objects needed for rollback must remain intact; eligible reuse is then limited or delayed. This retains a familiar STM write-buffer shape but needs a defined atomic publication and RC transfer protocol.
3. **In-place mutation with undo.** Lock/version the relevant object, save overwritten fields and ownership state, then restore both on abort or finalize reference changes on commit. This could preserve more in-place reuse, but the undo state, nested transactions, allocation, readers, and concurrent final drops all need to participate in the protocol. The sources reviewed here do not demonstrate this combination.

## Evidence Limits

The Perceus paper's proof concerns its own formal reference-counting calculus and cycle-free programs; the paper does not establish transactional semantics. Koka's implementation shows compiler-directed reuse and cross-thread RC, not STM. The STM papers and GHC implementation establish transactional logs, validation, and commit for their models; GHC's example stores closure pointers in TVar transaction records and does not establish Perceus count updates or reuse across commit/abort. No source cited here proves that Perceus and STM are incompatible, nor does the absence of a combined result in this review establish that no such implementation exists. What remains open for a memory-contract decision is the intended STM boundary (transactional roots versus arbitrary object fields), which effects/allocation are allowed in a transaction, and whether rollback must recover mutations to existing objects.
