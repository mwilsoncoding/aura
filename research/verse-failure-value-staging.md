# Verse Failure, Choice, and Compile-Time/Runtime Evidence

Research for [Aura issue #27](https://github.com/mwilsoncoding/aura/issues/27)

## Scope and Source Basis

The Epic-hosted [Failure in Verse](https://dev.epicgames.com/documentation/fortnite/failure-in-verse?lang=en-US) page is an Epic-published documentation entry point. During this investigation, its HTML response contained the documentation app shell and an hCaptcha challenge rather than the chapter text; the same applied to the [Verse Language Quick Reference](https://dev.epicgames.com/documentation/fortnite/verse-language-quick-reference?lang=en-US). I therefore do not attribute detailed semantic claims to those pages. This is a limit on what could be verified here, not evidence that Epic's docs lack further detail.

The usable source snapshot is [`verselang/book`](https://github.com/verselang/book/tree/2af9dfd79c46ce91623e00c9088a342842ad785b), pinned to commit `2af9dfd79c46ce91623e00c9088a342842ad785b`. It is published under the `verselang` GitHub organization, not Epic Games. Its README describes it as open-source Verse documentation, while its development notes say the `Tests/` directory is a verbatim copy of the compiler test suite and point to compiler/VM projects in Epic's `fortniteMain` tree. The test file cited below carries an Epic Games copyright notice. Accordingly, I treat the test as a public mirror of first-party compiler tests, and treat explanatory prose (including the book overview) as maintainer-authored material rather than as an Epic-published specification. ## Observed Verse Facts

### Failure Is Not an Explicit Result Payload

The clearest distinction in the compiler test is between a function's declared result type and its ability to fail. `f4` is declared `<transacts><decides>:int`: successful calls yield an `int`, while calls with values below its predicate are asserted as failure using `not f4[...]`. The test separately declares `f9` as `<transacts><decides>:?int`, exercising both function-level failure and a successful function call that returns an empty optional. That is evidence for an implicit failable computation/control-flow channel alongside the ordinary result type, not an implicit `Result<T,E>`-style return value with an error payload. The cited examples do not establish that Verse cannot represent errors as ordinary user data; they establish that this is not what `<decides>` itself returns. [Compiler test, `f4` and `f9`](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/Tests/Failure.versetest#L5-L19) · [Optional-return tests](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/Tests/Failure.versetest#L54-L60)

The maintainer-authored failure chapter describes ordinary failure as producing no value and distinguishes it from an exception. Its separate "Runtime Errors" section describes unrecoverable runtime errors that terminate execution. This is a useful distinction in that chapter, but the exception comparison is explanatory prose rather than text verified from the Epic-hosted page in this run. [Failure chapter, opening and failable expressions](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/docs/08_failure.md#L3-L71) · [Failure chapter, runtime errors](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/docs/08_failure.md#L816-L827)

Verse also has an explicit optional type, written `?T`, which can represent presence/absence as a value. The test's `f9` demonstrates the distinction: the function can fail before returning, or succeed with an empty optional; unwrapping that empty optional is itself failable. The failure chapter describes `option{...}` and `?` as the conversion boundary between optional values and failable expressions. An optional is therefore an explicit value container, but it is not evidence that every failed `<decides>` call returns an option, much less a value carrying an error reason. [Optional containers and conversions](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/docs/08_failure.md#L286-L305) · [Function-level versus optional-value outcomes](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/docs/08_failure.md#L492-L560) · [Compiler test](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/Tests/Failure.versetest#L54-L60)

### Propagation, Choice, and the Limits of "Backtracking"

The reference describes failure contexts as the places where failable expressions are handled. In its examples, failure of an expression in an `if` condition prevents the body from running; a failed iteration-domain expression skips that `for` iteration; and a `<decides>` function body is itself a failure context. It describes `and` as requiring both expressions to succeed, `not` as inverting success/failure, and `or` as trying alternatives in order until one succeeds. The compiler test includes a `decides` call combined with `or` and asserts the result. [Failure contexts](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/docs/08_failure.md#L73-L145) · [Failure logic and alternatives](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/docs/08_failure.md#L177-L221) · [Compiler test](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/Tests/Failure.versetest#L5-L11)

These sources support ordered alternatives and failure propagation. They do not, by themselves, establish the broader claim that Verse performs general Prolog-style search or retries an already-successful `or` alternative after a later, enclosing expression fails. The book overview's label "functional, logic, and imperative" and its prose about failure should not be expanded into that stronger operational guarantee without a more specific language reference or compiler test. [Book overview](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/docs/00_overview.md#L5-L13) · [Alternative semantics described by the failure chapter](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/docs/08_failure.md#L177-L221)

### Rollback Is an Effect/Transaction Behavior, Not Value Semantics

The failure chapter says mutable updates made inside a failure context are provisional and become permanent only if the context succeeds; its purchase example uses `<transacts><decides>` and shows a failed purchase rolling back an earlier balance update. This behavior concerns transactional effects. It should not be conflated with how values are copied or shared. [Speculative execution](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/docs/08_failure.md#L145-L175)

Separately, the mutability chapter says struct assignment makes a deep copy and describes classes as having reference semantics. The combination is thus: a failure context may roll back transactional mutations, while value/reference semantics determine whether ordinary assignments copy a data value or share an object. The source does not say that failure itself is a value or that value semantics alone provide rollback. [Struct copying and class references](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/docs/05_mutability.md#L208-L315) · [Effect definitions for `<decides>`, `<transacts>`, and `<computes>`](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/docs/13_effects.md#L95-L128)

### What the Reviewed Sources Establish About Staging

The public book overview explicitly claims that "the same language constructs work at both compile-time and run-time," and adds that Verse has no preprocessor. That is the book's stated design principle; the overview is in the `verselang/book` repository, not on an Epic-owned documentation host. The public compiler-test mirror and the reviewed failure/effect chapters establish behavior for constructs such as `<decides>`, `<transacts>`, `<computes>`, `if`, `for`, and optionals, but the inspected material does not show those constructs being evaluated in both compiler-time and runtime contexts or define a general staging contract. [Overview claim](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/docs/00_overview.md#L7-L15) · [Effects reference](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/docs/13_effects.md#L95-L128) · [Compiler failure tests](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/Tests/Failure.versetest#L5-L60)

In particular, the effect reference describes `<computes>` as a pure computation effect and `<decides>` as a success/failure effect. Those meanings do not, on their own, establish when computation runs. The sources reviewed here therefore do not verify the overview's broad compile-time/runtime claim as an Epic-documented or compiler-enforced contract. Since the canonical Epic documentation body was not retrievable, this is a bounded finding about the sources inspected, not a claim that no official source could establish it. [Effects reference](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/docs/13_effects.md#L100-L128) · [Epic Failure in Verse page](https://dev.epicgames.com/documentation/fortnite/failure-in-verse?lang=en-US)

## Possible Aura Design Implications (Not Decisions)

- Keep "a computation may fail" distinct from "the computation returns a value that encodes success or failure." Verse's `<decides>` tests show the former; Verse optionals show one explicit value-level absence representation. If Aura explores both, decide whether each channel is inspectable as ordinary data, propagated by control flow, or both. This does not recommend either representation. [Compiler failure/optional tests](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/Tests/Failure.versetest#L14-L19) · [Optional outcomes](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/Tests/Failure.versetest#L54-L60)
- Specify the scope of alternatives separately from the word "backtracking": whether alternatives are merely tried left-to-right on immediate failure, or can be revisited when a later enclosing computation fails. The evidence reviewed here settles the former example, not the latter. [Failure logic](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/docs/08_failure.md#L177-L221)
- Specify rollback boundaries and allowed effects independently from value/reference semantics. Verse's account associates rollback with failing transactional contexts, while its mutability account distinguishes copied structs from shared class references. [Failure transactions](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/docs/08_failure.md#L145-L175) · [Value/reference semantics](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/docs/05_mutability.md#L246-L315)
- Keep compile-time evaluation/staging as an open question. Do not infer it from effect names such as `<computes>`, or from the book overview's broad statement; the reviewed public artifacts do not establish the runtime/compile-time contract. This report makes no recommendation about Aura's module system or staging model. [Book overview](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/docs/00_overview.md#L7-L15) · [Effects reference](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/docs/13_effects.md#L100-L128)

## Source Gaps

The Epic-hosted documentation entry points were identified but their semantic content could not be inspected because the responses served a challenge/app shell. The public documentation repository points to compiler tests and source projects in `fortniteMain`, but does not contain the compiler implementation itself. Accordingly, this report treats the copied Epic-copyright test as primary behavioral evidence, attributes normative prose to the public book, and leaves broader backtracking and compile-time/runtime guarantees unresolved.
