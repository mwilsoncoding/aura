# Test and Benchmark Practices in Aura's Influence Set

Research for [Aura issue #30](https://github.com/mwilsoncoding/aura/issues/30), scoped to evidence relevant to [memory-safety obligations (#31)](https://github.com/mwilsoncoding/aura/issues/31), [test harness and correctness strategy (#32)](https://github.com/mwilsoncoding/aura/issues/32), and [early benchmarking practice (#33)](https://github.com/mwilsoncoding/aura/issues/33). This report records upstream observations separately from possible Aura implications; it does not choose Aura policy.

## Source Pins

Repository observations are pinned to Erlang/OTP `15e5d29a42dd058f15893f26ecf056f623bbb3e9`, Koka `8b803da69d3941ce1e03173578093aefc41ee548`, the public Verse book (`verselang/book`) at `2af9dfd79c46ce91623e00c9088a342842ad785b`, Elixir `648b2a94934664cfd2c788348d02d799c68faa69`, and Rust Miri `806a9332715f79794ee2b9c039ccb0f27154df49` ([OTP](https://github.com/erlang/otp/tree/15e5d29a42dd058f15893f26ecf056f623bbb3e9), [Koka](https://github.com/koka-lang/koka/tree/8b803da69d3941ce1e03173578093aefc41ee548), [Verse book](https://github.com/verselang/book/tree/2af9dfd79c46ce91623e00c9088a342842ad785b), [Elixir](https://github.com/elixir-lang/elixir/tree/648b2a94934664cfd2c788348d02d799c68faa69), [Miri](https://github.com/rust-lang/miri/tree/806a9332715f79794ee2b9c039ccb0f27154df49)). Perceus references the authors' paper, *Perceus: Garbage Free Reference Counting with Reuse*, DOI [10.1145/3453483.3454032](https://doi.org/10.1145/3453483.3454032), and its [Microsoft Research page](https://www.microsoft.com/en-us/research/publication/perceus-garbage-free-reference-counting-with-reuse/).

## Observations

### Test Harness and Correctness

- **Erlang/OTP:** OTP's testing guide describes its suites as Common Test suites, spread across applications, ERTS, and emulator directories; the `ts` wrapper supports running a whole application, a suite, or an individual case, so developers can narrow the feedback loop ([testing guide](https://github.com/erlang/otp/blob/15e5d29a42dd058f15893f26ecf056f623bbb3e9/HOWTO/TESTING.md)). The same guide describes substantial integration and platform-specific test fixtures, including generated or compiled native support code ([testing guide](https://github.com/erlang/otp/blob/15e5d29a42dd058f15893f26ecf056f623bbb3e9/HOWTO/TESTING.md)).
- **OTP property testing:** Common Test has an optional property-test adapter for QuickCheck, PropEr, or Triq; it compiles property modules in a `property_test` directory, runs properties through a Common Test suite, and stores output in the normal Common Test log ([property-testing guide](https://github.com/erlang/otp/blob/15e5d29a42dd058f15893f26ecf056f623bbb3e9/lib/common_test/doc/guides/ct_property_test_chapter.md)). OTP also carries concrete property suites, including hash, compiler, crypto, and Dialyzer examples ([OTP property-test paths](https://github.com/erlang/otp/tree/15e5d29a42dd058f15893f26ecf056f623bbb3e9/erts/emulator/test/property_test), [compiler properties](https://github.com/erlang/otp/tree/15e5d29a42dd058f15893f26ecf056f623bbb3e9/lib/compiler/test/property_test)). This is evidence that property tests can sit inside the existing suite/reporting system, not evidence that every OTP component uses them.
- **OTP model-based property testing:** Its stateful crypto property defines a model state, commands, preconditions, postconditions, and state transitions, then generates parallel command sequences and checks decryption against modeled plaintext ([stateful crypto property](https://github.com/erlang/otp/blob/15e5d29a42dd058f15893f26ecf056f623bbb3e9/lib/crypto/test/property_test/crypto_ng_api_stateful.erl)).
- **Verse fuzz regressions:** `ParserFuzzingBugs.versetest` stores malformed parser inputs and asserts syntax-error codes; it is evidence of minimized/saved regression cases, not by itself evidence of an active fuzz generator in the test runner ([parser-fuzzing regressions](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/Tests/Bugs/2022-11-30-ParserFuzzingBugs.versetest)).
- **Koka:** Koka combines Hspec unit tests for compiler utilities with executable `.kk` tests whose expected stdout is stored in adjacent `.out` files; its test runner compares sanitized actual and expected output, and has a mode for writing expected results ([Hspec tests](https://github.com/koka-lang/koka/blob/8b803da69d3941ce1e03173578093aefc41ee548/test/NameSpec.hs), [golden runner](https://github.com/koka-lang/koka/blob/8b803da69d3941ce1e03173578093aefc41ee548/test/Spec.hs), [effect test and expected output](https://github.com/koka-lang/koka/tree/8b803da69d3941ce1e03173578093aefc41ee548/test/algeff)). This preserves runnable language behavior and output as regression artifacts, while normalization reduces incidental platform/path/name differences in comparisons ([golden runner](https://github.com/koka-lang/koka/blob/8b803da69d3941ce1e03173578093aefc41ee548/test/Spec.hs)).
- **Verse:** The public `verselang/book` repository separates extracted documentation-snippet tests from the mirrored compiler `.versetest` suite; `testall.sh` runs snippets by chapter, while `bin/vtest` runs a file or directory and reports per-file results and a summary ([snippet runner](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/testall.sh), [test runner](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/bin/vtest)). The runner selects the Verse TestScript VM for `.versetest` inputs, and the development guide documents `assert_semantic_error(<code>)` fixtures for expected compiler errors ([test runner](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/bin/vtest), [semantic-error regression](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/Tests/Bugs/2020-08-05-UnusedArchetypeUseAfterFree.versetest)). The book also includes bug-named use-after-free cases as regression programs, such as data-member attributes and coercion of nested structs to dynamically typed values ([data-member regression](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/Tests/Bugs/2020-04-21-DataMemberAttributeUseAfterFree.versetest), [nested-struct regression](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/Tests/Bugs/2023-02-20-UseAfterFreeWhenCoercingNestedStructsToDynamicallyTypedValue.versetest)). These are targeted regressions, not a general proof or a documented memory checker.
- **Elixir:** ExUnit supports unit cases and assertions, and Mix's documented `mix test` workflow discovers `*_test.exs` under `test/` ([ExUnit source documentation](https://github.com/elixir-lang/elixir/blob/648b2a94934664cfd2c788348d02d799c68faa69/lib/ex_unit/lib/ex_unit.ex)). Elixir's parser tests assert produced ASTs and expected syntax exceptions ([parser tests](https://github.com/elixir-lang/elixir/blob/648b2a94934664cfd2c788348d02d799c68faa69/lib/elixir/test/elixir/kernel/parser_test.exs)); diagnostic tests capture and compare complete formatted compiler-error output, including source spans and markers ([diagnostic tests](https://github.com/elixir-lang/elixir/blob/648b2a94934664cfd2c788348d02d799c68faa69/lib/elixir/test/elixir/kernel/diagnostics_test.exs)). Those fixtures exercise semantic outputs and diagnostic stability rather than only process exit status.

### Memory Safety and Reference Accounting

- **Perceus (formal result):** The authors describe Perceus as precise reference counting with reuse and specialization, formalize it in a linear resource calculus, and state that they prove the algorithm sound and garbage-free; reuse analysis enables guaranteed in-place updates in the formalized setting ([authors' paper page](https://www.microsoft.com/en-us/research/publication/perceus-garbage-free-reference-counting-with-reuse/), [DOI](https://doi.org/10.1145/3453483.3454032)). This is a static/formal result about the model and algorithm; it is not evidence that an arbitrary compiler/runtime implementation or its generated code is memory-safe.
- **Koka (runtime reference-count observations):** A Koka language test reaches into the C runtime to read a block's reference count before and after a control-effect/capture sequence and records expected values `(1,1)` and `(1,0)` ([reference-count fixture](https://github.com/koka-lang/koka/blob/8b803da69d3941ce1e03173578093aefc41ee548/test/cgen/simple-refcount.kk)). The C reference-counting path also contains internal assertions that a block being freed has count zero and that child pointers designate valid blocks ([reference-count implementation](https://github.com/koka-lang/koka/blob/8b803da69d3941ce1e03173578093aefc41ee548/kklib/src/refcount.c)). These are runtime assertions/checks and test observations; they do not establish all paths preserve counts or avoid use-after-free.
- **Erlang/OTP (instrumented emulator):** OTP's test guide documents running selected Common Test suites with AddressSanitizer or Valgrind builds, directing developers to inspect the resulting reports ([ASan/Valgrind instructions](https://github.com/erlang/otp/blob/15e5d29a42dd058f15893f26ecf056f623bbb3e9/HOWTO/TESTING.md)). These are dynamic instrumentation of executed native-emulator paths, distinct from a language-level static guarantee and limited by the exercised runs.
- **Verse:** The cited Verse use-after-free fixtures preserve scenarios associated with prior bugs, while the runner executes them in the TestScript VM ([nested-struct regression](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/Tests/Bugs/2023-02-20-UseAfterFreeWhenCoercingNestedStructsToDynamicallyTypedValue.versetest), [runner](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/bin/vtest)). In the sources reviewed here, these are regression tests; I found no claim that they instrument or prove general memory safety.
- **Rust, narrowly applicable:** Miri is a nightly interpreter that can run Rust test suites and report undefined behavior such as out-of-bounds access, use-after-free, invalid uninitialized-data use, and leaks ([Miri README](https://github.com/rust-lang/miri/blob/806a9332715f79794ee2b9c039ccb0f27154df49/README.md)). Its own documentation cautions that it tests particular executions, may miss other nondeterministic executions, and cannot establish soundness; its status is dynamic checking, not proof ([Miri limitations](https://github.com/rust-lang/miri/blob/806a9332715f79794ee2b9c039ccb0f27154df49/README.md)). This is relevant only if Aura's compiler/runtime implementation or a Rust code-generation path contains Rust code whose unsafe behavior can actually be exercised under Miri; it is not a substitute for the other influences or a checker for arbitrary generated targets.

### Benchmarks and Performance Baselines

- **Erlang/OTP:** OTP runs benchmarks through the Common Test/`ts` infrastructure, stores results in timestamped directories, and collects multiple runs for each benchmark ([benchmarking guide](https://github.com/erlang/otp/blob/15e5d29a42dd058f15893f26ecf056f623bbb3e9/HOWTO/BENCHMARKS.md)). Its guidance asks benchmark cases to report raw values rather than pre-averaging, leaving averages, means, standard deviation, and other aggregation to the result tooling ([benchmarking guide](https://github.com/erlang/otp/blob/15e5d29a42dd058f15893f26ecf056f623bbb3e9/HOWTO/BENCHMARKS.md)). The same guide warns that feature-specific benchmarks can become outdated, which makes benchmark maintenance part of the evidence rather than assuming every checked-in workload remains representative ([benchmarking guide](https://github.com/erlang/otp/blob/15e5d29a42dd058f15893f26ecf056f623bbb3e9/HOWTO/BENCHMARKS.md)).
- **Koka:** Koka's benchmark helper explicitly adopts a Criterion-like grouping, separates pre/run/post actions, lazily constructs a shared environment, and notes that retaining the environment through the last benchmark avoids freeing it during measurement in a reference-counted runtime ([benchmark helper](https://github.com/koka-lang/koka/blob/8b803da69d3941ce1e03173578093aefc41ee548/test/perf/benchmark.kk)). The checked-in example times each benchmark with one `elapsed` call and prints the result; this file alone does not document repeated samples, warm-up, statistical aggregation, or noise control ([benchmark helper and example](https://github.com/koka-lang/koka/blob/8b803da69d3941ce1e03173578093aefc41ee548/test/perf/benchmark.kk)).
- **Perceus evaluation:** The Perceus paper reports measured performance comparisons for its Koka implementation, so its performance claims are experimental results in addition to the paper's separate formal result ([authors' paper page](https://www.microsoft.com/en-us/research/publication/perceus-garbage-free-reference-counting-with-reuse/)). That does not itself specify an early-project baseline process.
- **Scope limit:** In the pinned Verse book and Elixir source material examined for this report, I found test/profiler examples but no first-party, repeatable benchmark-baseline protocol to characterize; this is a limit of the material reviewed, not a claim that no such practice exists elsewhere ([Verse sampling-profiler fixture](https://github.com/verselang/book/blob/2af9dfd79c46ce91623e00c9088a342842ad785b/Tests/SamplingProfiler.versetest), [Elixir source tree at pinned revision](https://github.com/elixir-lang/elixir/tree/648b2a94934664cfd2c788348d02d799c68faa69)).

## Possible Aura Implications (Not Decisions)

- **For #32, harness shape:** The examples provide evidence for considering small tests at distinct compiler/runtime seams, executable semantic examples with stable expected output, exact negative/diagnostic fixtures, and property tests where an invariant can be stated independently of specific examples; OTP demonstrates that property tests can be integrated into normal test reporting ([Koka golden runner](https://github.com/koka-lang/koka/blob/8b803da69d3941ce1e03173578093aefc41ee548/test/Spec.hs), [Elixir diagnostic tests](https://github.com/elixir-lang/elixir/blob/648b2a94934664cfd2c788348d02d799c68faa69/lib/elixir/test/elixir/kernel/diagnostics_test.exs), [OTP property guide](https://github.com/erlang/otp/blob/15e5d29a42dd058f15893f26ecf056f623bbb3e9/lib/common_test/doc/guides/ct_property_test_chapter.md)). The sources show these as complementary test roles, not as a requirement to copy any one language's harness.
- **For #31, evidence layers:** The sources distinguish a proof over a formal reference-counting model, runtime accounting assertions, instrumented native executions, and bug-specific regression programs ([Perceus paper](https://doi.org/10.1145/3453483.3454032), [Koka refcount test](https://github.com/koka-lang/koka/blob/8b803da69d3941ce1e03173578093aefc41ee548/test/cgen/simple-refcount.kk), [OTP instrumentation guide](https://github.com/erlang/otp/blob/15e5d29a42dd058f15893f26ecf056f623bbb3e9/HOWTO/TESTING.md), [Verse memory regressions](https://github.com/verselang/book/tree/2af9dfd79c46ce91623e00c9088a342842ad785b/Tests/Bugs)). A future test obligation can therefore be tied to the chosen Aura memory contract and state exactly which layer checks it; no single finite test run should be described as proving general memory safety.
- **For #33, baseline questions:** OTP supports collecting repeated raw observations for later statistical analysis, while Koka's small helper illustrates explicit workload setup/teardown and how reference-counted environment lifetime can affect what is measured ([OTP benchmark guidance](https://github.com/erlang/otp/blob/15e5d29a42dd058f15893f26ecf056f623bbb3e9/HOWTO/BENCHMARKS.md), [Koka benchmark helper](https://github.com/koka-lang/koka/blob/8b803da69d3941ce1e03173578093aefc41ee548/test/perf/benchmark.kk)). For Aura, these sources motivate asking which measurements are currently meaningful, what setup is inside or outside the timed region, and what run metadata/statistics are needed to compare results; they do not determine the workloads or thresholds.
