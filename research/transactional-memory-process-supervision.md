# Transactional Memory Versus Process Supervision

## Finding

**Answer:** A BEAM/OTP supervisor tree alone does not provide transactional isolation or rollback. OTP supervision specifies child-process lifecycle, failure observation, shutdown, and restart behavior; STM specifies how participating operations on shared transactional memory appear to commit or abort atomically. These are distinct mechanisms. That conclusion is an implication of the guarantees documented by OTP and the STM papers, not a statement that OTP forbids an STM facility from being used alongside supervision. ([OTP Supervisor Behaviour](https://www.erlang.org/docs/28/system/sup_princ.html); [OTP `supervisor` module](https://www.erlang.org/docs/28/apps/stdlib/supervisor.html); [Shavit and Touitou, 1995](https://doi.org/10.1145/224964.224987); [Harris et al., 2005](https://doi.org/10.1145/1065944.1065952))

## Transaction Semantics

**Paper facts.** Software transactional memory applies the transaction abstraction to shared memory: transactions group reads and writes so an execution can take effect as a unit rather than exposing a partially completed update. The foundational STM proposal is Shavit and Touitou's *Software Transactional Memory*; Harris, Marlow, Peyton Jones, and Herlihy's *Composable Memory Transactions* develops a compositional transactional model. ([Shavit and Touitou, 1995](https://doi.org/10.1145/224964.224987); [Harris et al., 2005](https://doi.org/10.1145/1065944.1065952); [Microsoft Research paper record and author abstract](https://www.microsoft.com/en-us/research/publication/composable-memory-transactions/))

In STM, **atomicity** concerns the visibility of a transaction's memory update: its writes are committed as one transaction or are not published as a partial transaction. **Isolation** concerns concurrent transactions over the shared transactional state: their interleaving is constrained by the STM model, commonly described in terms of an equivalent serial execution. Those are transaction-level properties, not consequences of placing the processes that run transactions beneath a supervisor. The cited papers study transactional memory, while OTP's supervisor specification is about processes and child specifications. ([Shavit and Touitou, 1995](https://doi.org/10.1145/224964.224987); [Harris et al., 2005](https://doi.org/10.1145/1065944.1065952); [OTP `supervisor` module](https://www.erlang.org/docs/28/apps/stdlib/supervisor.html))

**Commit and abort.** A transaction that succeeds commits its transactional memory changes; an attempt that cannot satisfy the STM's concurrency or control-flow rules can abort or retry, without exposing its tentative writes as a committed partial result. Conflict detection and retry/abort policy are implementation/model details; it would be too strong to claim that every STM uses the same detection algorithm or resolves every conflict identically. ([Shavit and Touitou, 1995](https://doi.org/10.1145/224964.224987); [Harris et al., 2005](https://doi.org/10.1145/1065944.1065952))

**Shared-state conflicts.** Conflicts are meaningful because transactions access overlapping shared transactional state. An STM coordinates those accesses so that conflicting concurrent updates do not both become visible in a way that violates its transaction semantics; an implementation may reject or restart an attempt, or otherwise serialize the conflicting work. This refers to state enrolled in the STM mechanism, not every value, message, file, or external service touched by the surrounding process. ([Shavit and Touitou, 1995](https://doi.org/10.1145/224964.224987); [Harris et al., 2005](https://doi.org/10.1145/1065944.1065952))

**Rollback boundary.** STM rollback means abandoning an uncommitted transactional-memory attempt; it does not, by that fact alone, undo arbitrary effects outside that transactional memory. This follows from the papers' stated subject—transactions over memory—and is not a guarantee about an arbitrary external database, I/O operation, or message delivery. Thus “rollback” should not be read as general process-state or world-state restoration. ([Shavit and Touitou, 1995](https://doi.org/10.1145/224964.224987); [Harris et al., 2005](https://doi.org/10.1145/1065944.1065952))

## Supervision Semantics

**OTP facts.** OTP defines a supervisor as a process responsible for starting, stopping, and monitoring child processes, with restart behavior configured by child specifications and supervisor flags. The documented strategies include `one_for_one`, `one_for_all`, and `rest_for_one`; these select which children are affected when a child terminates. Child restart types distinguish `permanent` (always restarted), `transient` (restarted after abnormal termination), and `temporary` (not restarted). ([OTP Supervisor Behaviour, OTP 28](https://www.erlang.org/docs/28/system/sup_princ.html); [OTP `supervisor` module, OTP 28](https://www.erlang.org/docs/28/apps/stdlib/supervisor.html); [OTP `supervisor.erl`, tag OTP-28.0](https://github.com/erlang/otp/blob/OTP-28.0/lib/stdlib/src/supervisor.erl))

Supervision also bounds repeated failure: if restart intensity exceeds its configured limit during the configured period, the supervisor terminates its children and itself. This is a lifecycle/restart limit, not a transaction conflict limit or a rollback operation. ([OTP `supervisor` module, OTP 28](https://www.erlang.org/docs/28/apps/stdlib/supervisor.html); [OTP `supervisor.erl`, tag OTP-28.0](https://github.com/erlang/otp/blob/OTP-28.0/lib/stdlib/src/supervisor.erl))

At the process level, Erlang links propagate exit signals according to the receiver's exit-trapping state and the signal's reason; monitors instead report process termination to the monitoring process with a `DOWN` message. OTP's supervisor documentation describes monitoring child processes and waiting for an exit signal during graceful shutdown. These are failure/lifecycle observations and responses; they do not specify a shared-memory transaction's read set, write set, isolation, commit point, or rollback. ([Processes, OTP 28](https://www.erlang.org/docs/28/system/ref_man_processes.html); [OTP Supervisor Behaviour, OTP 28](https://www.erlang.org/docs/28/system/sup_princ.html))

## Relationship and Coexistence

**Implication: supervision alone is insufficient.** A supervisor can detect that a child exited and apply its configured restart policy, but restart does not make earlier reads and writes atomic, isolate concurrent children, identify STM conflicts, or reverse effects that already escaped the child. Those missing guarantees belong to a transaction mechanism, not to child lifecycle policy. ([OTP `supervisor` module, OTP 28](https://www.erlang.org/docs/28/apps/stdlib/supervisor.html); [Processes, OTP 28](https://www.erlang.org/docs/28/system/ref_man_processes.html); [Harris et al., 2005](https://doi.org/10.1145/1065944.1065952))

**Implication: they can coexist.** A process may be supervised for lifecycle while its operations on shared state use STM for transactional isolation and commit/abort. In such a composition, STM defines what happens to an in-flight, uncommitted memory transaction; supervision defines what happens to the process after failure, including whether and when a replacement child starts. OTP documentation does not prescribe how an STM runtime handles a process dying during a transaction, nor does it make restarted work exactly-once; those details would depend on the STM/runtime and application protocol. ([OTP Supervisor Behaviour, OTP 28](https://www.erlang.org/docs/28/system/sup_princ.html); [OTP `supervisor` module, OTP 28](https://www.erlang.org/docs/28/apps/stdlib/supervisor.html); [Shavit and Touitou, 1995](https://doi.org/10.1145/224964.224987); [Harris et al., 2005](https://doi.org/10.1145/1065944.1065952))

For example, an STM commit can govern visibility of a shared-memory update, while a supervisor independently restarts a child that later crashes. Conversely, if a child sends a message or performs another external effect before it crashes, neither the restart policy nor memory-transaction rollback implies that the already-performed effect is withdrawn. This is an implication of the memory-only scope of the cited STM work and OTP's separate process/message and restart semantics. ([Harris et al., 2005](https://doi.org/10.1145/1065944.1065952); [Processes, OTP 28](https://www.erlang.org/docs/28/system/ref_man_processes.html); [OTP `supervisor` module, OTP 28](https://www.erlang.org/docs/28/apps/stdlib/supervisor.html))
